# Spec rules

Always in effect. How the `.specs/` tree works — kept short since it loads every session.

## Layout
```
.specs/
├── INDEX.md            routing table: code-path glob → owning spec (generated)
├── 00-brief.md         root spec, no parent
├── 01-architecture.md  parent: 00-brief
├── 02-tech.md          parent: 00-brief
├── contracts/          optional, see "Writing" below, parent: 01-architecture
└── features/           one file per feature, parent: 01-architecture (or a contract, or another feature)
```
`INDEX.md` is generated by `spec-sync` — never hand-edit it. A spec's own `status` and checkboxes
are its state; `INDEX.md` only routes code path → owning spec. For handing work to a context with
no repo access, use `session-snapshot` instead.

## Frontmatter
Required: `id`, `title`, `parent`, `status`.

```yaml
---
id: feature.checkout          # unique, dot-namespaced
title: Checkout flow
parent: 01-architecture       # id of the parent spec; only 00-brief has parent: null
status: active                # draft | active | superseded
owns:                         # glob(s) this spec is the source of truth for; [] is valid
  - "src/checkout/**"
jira: TZG-1234                # optional pointer, not a synced mirror
related: [feature.cart, 02-tech]
updated: 2026-01-01
---
```

## Writing

| Rule | Detail |
|---|---|
| One owner per file | Longest matching glob in `owns` wins. Two equal-specificity globs matching the same file is a bug — flag it. |
| No match in `INDEX.md` | Expected on a partially-specced codebase, not a blocker. Proceed with the code you have; write a spec only if the task is substantial enough to be worth finding later. |
| Unspecced areas | Normal, not an error. `spec-sync --check` fails only on real problems (dangling glob, ambiguous ownership) — never on missing coverage. |
| Acceptance criteria | Full Given/When/Then, named, per `.agents/templates/spec-feature.md`. A one-line "- [ ] retry on failure" isn't actionable. |
| Don't duplicate a parent | Link to it, state only the delta. |
| `Solution`/`References` | Filled in after implementation and review, not at spec-creation time. |
| Contracts | Only for work spanning multiple modules — `.agents/templates/spec-contract.md`, `owns: []`, full AC at product level. Feature specs underneath reference which they satisfy via `Implements`, not repeat them. Whether a task gets its own spec or folds into an existing one is a size call, not a rule. A module referenced in a contract's Implementation table doesn't have to be its structural child — its own `parent` can be `architecture` directly if it's a shared component other contracts also rely on. |
| Specs aren't written upfront | Write or update one as development uncovers the need — that's what `spec-from-code` is for. |
| `jira:` | A pointer to the spec's origin ticket, not a synced mirror. Ticket status and spec `status` answer different questions — don't keep them in lockstep by hand. |
| Ticket-driven change | Add a row to the spec's `Change history` section (create it if missing) naming the ticket and what changed, in the same commit as the edit — append-only, never overwrite a row. The Ticket column may say "No ticket" when there wasn't one — a hotfix, a direct request, a `spec-from-code` reconciliation, or a spec bootstrapped from existing code. |

## Keeping it honest

| Rule | Detail |
|---|---|
| Adding public surface | Extend the owning feature spec in the same change. |
| Deleting/moving code | Update `owns`, re-run `spec-sync`. |
| Code changed, spec now stale | Use `spec-from-code` (code is truth) — `spec-sync` only checks structure, not whether prose still matches behavior. |
| Spec changed ahead of code | Use `spec-to-code` (spec is truth). Both skills are direct-request only. |
